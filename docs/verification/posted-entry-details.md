# 正式账目明细追问与草稿意图分流

2026-10-19。复现使用者先问“看一下我今天花了多少钱”，再问“具体的账目给我看一下”，却收到“本会话没有待确认草稿”。

## 已确认原因与版本边界

旧版在微信入口先运行草稿意图分类器，只给分类器当前文字和草稿状态，没有上一条正式查询的条件。真实模型通过完整 WechatBot 收件、分类、会话及发送流程复现：第二条消息只增加分类调用，未进入正式查账会话，直接返回没有草稿。此外，原查询协议仅有汇总、分组和趋势，没有逐笔明细结果。

先前验证直接调用微信专用 Conversation 接口，绕过了 WechatBot 入口的分类和发送处理，因此不能证明这条流程通过。本轮保留这一覆盖缺口，不用后面的查询成功代替入口验证。

## 最小修复

- 普通会话和微信的共同分类器接收当前会话的上一条权威查询条件；明确区分正式账目明细、待确认草稿和入账同意。查看明细属于只读查询，不赋予确认权限。
- `query_ledger` 新增 `entries` 视图及分页，沿用原日期、币种、类目、标签和关键词，直接复用受保护账目查询。每页 5 笔，包含名称、日期、类型、原币与折合金额、分类、标签及独立备注；退款使用自身备注和发生日期。
- 只在明确请求明细时读取逐笔内容；普通汇总不把逐笔备注发送给模型。模型的金额仍使用明确币种的主单位字符串，业务记录及原工具历史保持最小单位整数。
- 备注在聊天中最多显示 200 个 Unicode 码点，并标记节选；完整备注在账目和备份中保留。微信逐笔渲染 Markdown，长消息整条保留可见条目并明确说明仅显示部分，不截断一条后静默跳到下一页。网页与手机聊天卡片也展示同一份明细。
- 后续查询重新读取当前记录，条件变化重置页码，入账后的同轮报表刷新同步刷新明细。账目查询与报表版本不一致时拒绝混合结果。
